# RI Assistant — техническое задание

**Версия:** 2.0  
**Статус:** утверждённый план; реализация ежедневных брифов ещё не начата  
**Главный интерфейс:** существующий Telegram-бот **RI Assistant**

## 1. Цель

RI Assistant — единый цифровой помощник руководителя в Telegram. Утром он
показывает реальный план календаря и сжатый обзор входящей почты. Голосовые
функции календаря развиваются в том же Assistant, но не создают отдельного
пользовательского бота.

На данном этапе реализуются две ежедневные функции:

1. **Morning Calendar Brief** — в 08:00 Moscow.
2. **Morning Mail Brief** — в 08:05 Moscow.

## 2. Границы и изоляция проектов

- Работы выполняются только на AI Prod 01 (`165.232.68.212`). VPN VPS не
  используется.
- RI Assistant, Mail Brief и Cosmestetica — независимые Docker-проекты.
  Работа над RI Assistant/Mail Brief не меняет контейнеры, сети, базы,
  credentials или конфигурацию Cosmestetica, Carrier Agent и других проектов.
- PostgreSQL другого проекта не используется. Для почтового статуса первого
  этапа применяется отдельная persistent n8n Data Table **RI Assistant Mail
  Ledger** в контуре n8n.
- Полные тексты писем, вложения, токены и пароли не сохраняются в таблицах,
  GitHub, документах или логах.

## 3. Существующие компоненты, которые переиспользуются

| Компонент | Использование |
| --- | --- |
| `Morning agenda` workflow | Триггер 08:00 Moscow, Google Calendar, Telegram RI Assistant |
| `Mail Brief` workflow | Реальные Gmail и IMAP-подключения, классификация, Telegram RI Assistant |

## 4. Morning Calendar Brief — 08:00 Moscow

### Источник и правила

- Получать реальные события текущего дня из Google Calendar.
- Рассчитывать плановый диапазон дня **08:00–23:00 Moscow**, включая рабочие,
  личные, обучающие и спортивные события.
- Сортировать события по времени.
- Рассчитывать свободные окна внутри диапазона. Базовый буфер вокруг встреч —
  30 минут; окно показывается, если после буферов остаётся не менее 30 минут.
- Фиксировать пересечения, если интервалы событий накладываются.
- События на весь день показывать отдельной строкой и учитывать как блок дня,
  когда календарь помечает их как занятость.
- На один запуск формировать ровно одно Telegram-сообщение.

### Формат

```text
☀️ План на 19.09

08:30–09:30 — Английский
12:00–13:00 — Встреча с …
19:00–20:00 — Спорт

Свободные окна:
• 10:00–11:30
• 13:30–18:30
• 20:30–23:00

Конфликтов нет.
```

Если событий нет:

```text
☀️ План на 19.09

На сегодня запланированных мероприятий нет.
Свободное время: 08:00–23:00.
```

## 5. Morning Mail Brief — 08:05 Moscow

### Источники

Используются существующие реальные подключения Gmail и IMAP-почтовых ящиков.
Новые пользовательские боты, mock data, demo flows и имитации не применяются.

### Формат

```text
📬 Почта за 18.09

🔴 Important
• Анна Петрова — договор на согласование
  rshaidi@mail.ru · ответ требуется

🟡 Medium
• Банк — документы по заявке
  rishgroup@yandex.ru · ответ не требуется

⏳ Awaiting Reply
• ООО «…» — коммерческое предложение
  с 16.09 · rinat.fsin@mail.ru · ответ требуется

⚪ Other
• 6 newsletters · 4 notifications · 2 advertising
```

- **Important** и **Medium**: отправитель, тема или короткая суть, ящик,
  состояние ответа.
- **Other**: только агрегированные категории; отдельные письма не выводятся.
- **Awaiting Reply**: все открытые Important/Medium из предыдущих и текущих
  периодов. Запись не исчезает с окончанием суток.

## 6. RI Assistant Mail Ledger

Для каждого Important/Medium письма хранится минимум:

| Поле | Назначение |
| --- | --- |
| `source`, `mailbox` | Почтовый провайдер и конкретный ящик |
| `provider_message_id`, `rfc_message_id` | Устойчивый ключ письма |
| `thread_id` | Связь Gmail-писем в одной цепочке |
| `from_name`, `from_email`, `subject`, `body_preview` | Краткое представление без полного тела письма |
| `received_at`, `first_seen_at`, `last_seen_at`, `last_briefed_at` | История и отсутствие потерь между брифами |
| `priority` | `important`, `medium`, `other` |
| `reply_required` | `required`, `not_required`, `unknown` |
| `reply_status` | `awaiting_reply`, `answered`, `no_reply_required`, `closed` |
| `reply_message_id`, `answered_at`, `match_confidence` | Подтверждение реального исходящего ответа |
| `closed_at`, `closed_reason` | Явное закрытие RI без подмены статуса «ответил» |

### Логика статусов

- `awaiting_reply`: ответ требуется, но исходящий ответ ещё не найден.
- `answered`: найден реальный исходящий ответ в той же Gmail-цепочке либо по
  IMAP-заголовкам `In-Reply-To` / `References`.
- `no_reply_required`: письмо не требует действия по смыслу.
- `closed`: RI явно закрыл вопрос.
- Факт прочтения остаётся дополнительным индикатором; прочтение само по себе
  не переводит письмо в `answered` и не убирает его из Awaiting Reply.

## 7. Execution path

1. В 08:00 `Morning agenda` читает Google Calendar, нормализует события,
   вычисляет окна и конфликты, затем отправляет один Calendar Brief.
2. Mail collection считывает метаданные реальных писем за предыдущий день и
   idempotent-upsert записывает их в RI Assistant Mail Ledger.
3. Reply-status refresh просматривает Gmail Sent/Gmail threads и IMAP Sent,
   сопоставляет реальные ответы с открытыми входящими письмами.
4. В 08:05 Mail Brief строит новый дневной срез и постоянный Awaiting Reply,
   после чего отправляет одно сообщение в RI Assistant.
5. Реестр не очищается после брифа. Закрываются только письма с подтверждённым
   ответом, `no_reply_required` или явным закрытием RI.

## 8. Последовательность реализации

1. Удалить штатным интерфейсом n8n неактивный исторический workflow `Mail Agent`.
2. Доработать Calendar Brief и проверить один реальный выпуск на событиях и
   один выпуск без событий.
3. Создать RI Assistant Mail Ledger и внедрить идемпотентный сбор метаданных.
4. Добавить проверку исходящих ответов сначала для Gmail, затем для IMAP.
5. Сформировать новый Mail Brief и проверить жизненный цикл одного реального
   письма: `awaiting_reply` → `answered` / `closed`.
6. Отключить и удалить устаревшую временную логику Mail Brief только после
   успешной приёмки нового полного цикла.

## 9. Критерии приёмки

| Сценарий | Ожидаемый результат |
| --- | --- |
| День с событиями | В 08:00 приходит одно сообщение с реальными событиями, окнами и конфликтами |
| День без событий | В 08:00 приходит одно сообщение, что событий нет, и окно 08:00–23:00 |
| Письмо требует ответа | Оно попадает в Awaiting Reply и остаётся там в следующие дни |
| Письмо прочитано без ответа | Оно остаётся Awaiting Reply |
| На письмо отправлен ответ | Статус становится `answered`, письмо больше не показывается как открытое |
| Письмо закрыто RI | Статус становится `closed` без ложной отметки `answered` |
| Категория Other | Письма показаны только агрегированными числами |
| Утренний запуск | Каждый бриф отправляется ровно один раз |
